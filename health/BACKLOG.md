# health/ 未接入项（Backlog）

> **为什么有这个文件**：缺口如果只活在某个人的记忆里、或一份 gitignore 掉的本机计划文件里，
> 就等于没记——这正是本工具自己在治的病（「证据过期 = 假阴性」「决策不落账 = 没有』低频『只有』无数据『」）。
> 所以未接入项要和代码放在一起、进版本控制、每项带**触发条件**。
>
> **用法**：不要定期通读。当某项的**触发条件**出现时，来做它。
> 触发条件写的是"什么事实出现就该动手"，不是一个日期——日期会过期，事实不会。
>
> 最后更新：2026-09-23

## 1. Windows 无通知、无调度

- **现象**：三个 Python 脚本跨平台，但 `install.sh`（launchd）与 `skill-health-check.sh`（osascript）
  是 macOS 专有。Windows 用户只能手动跑脚本，收不到通知、也没有自动巡检。
- **为什么现在不做**：开发机无 Windows / 无 pwsh，**一行都验证不了**；
  而静默失效的调度注册比没有更糟（让人以为监控开着）。
- **触发条件**：有可实跑的 Windows 环境（或团队确实有 Windows 使用者提出需要）。
  交付物：`skill-health-check.ps1` + 一次性计划任务注册，需在 Windows 上实跑确认。
- **证据在哪**：README「平台边界」表。
- **2026-09-23 更新**：用户指出可参考 `yztcit/claude_plugins` 的 ps1（已验证）。
  但**范围有差**——那边两个 ps1 做的是插件安装/更新，**不含通知与定时调度**，
  故只作风格/结构参照，不构成本项的现成解。若「验证环境」确实存在（用户既已验过那边），
  本项的「无环境」硬卡即解除，降级为「待写 + 待验」。

## 2. 流水线 B：回归门禁（防退化）

- **现象**：没有任何"谁做得好"的度量。用量侧只能回答"谁没人用"，
  驱动得了**退役**，驱动不了**改进**。
- **为什么现在不做**：原计划的推迟理由是"待数据积累"——但该理由**自我否定**：
  转录 30 天过期、且裁决端从未触发，不主动做就永远不会积累。
  另一条否决：不建通用 eval，应从真实转录里挖**失败证据**（用户纠正/重做、
  以及 gen-commit 提议 vs 实际 `git log` 这类确定性信号）→ 聚类 → 出 SKILL.md diff → 小样本 A/B。
- **触发条件（2026-09-22 修正，旧条件已证不可达）**：旧写「失败成簇」——但
  `failures` 只测**机制级失败**（技能找不到/调用崩），不测"干得烂"，**结构性地接近 0**
  （实测 47 次调用全 0，join 已验证有效）。真正的质量信号是「用户推翻/重做」，实测
  **1–2 / 47 次**（~3%）——存在但太稀疏。而 30 天全库仅 47 次 skill/agent 调用，
  这个量级上谈质量趋势就是噪声。
  **修正后的条件**：①某个资产的调用量达到可统计规模（经验值 ≥20 次/30 天），
  使"推翻率"不再是 2 次 vs 1 次的抖动；或②出现**同一条编辑意见反复被推翻**的具体案例
  （即"这个 skill 总是做错同一件事"，此时不需要统计量、单例即足够）。
- **证据在哪**：设计文档 §4.2 流水线 B；上述实测数字见设计文档 §十六。

## 3. 流水线 C：漂移检测

- **现象**：官方 marketplace 或依赖（graphify）大版本更新时，没有任何自动检测，
  全靠人"想起来去看"。
- **为什么现在不做**：尚无因上游变更造成实际损害的案例。
- **触发条件**：官方/依赖更新**实际打断过**本套能力（如官方 code-review 改了语义、
  graphify 命令变更导致 `graphify-search` 失效）。
- **证据在哪**：设计文档 §4.3。

## 4. `update-plugins.ps1` 未经验证

- **现象**：团队仓库的 `update-plugins.ps1` 与 `.sh` 逻辑等价（内容指纹判定
  + 只处理已安装 scope），但**从未在 PowerShell 里跑过**。
- **为什么现在不做**：开发机无 pwsh。已写成「指纹计算失败即降级回原有 update 行为」，
  最坏情况是退化成旧行为而非报错中断，风险有界。
- **触发条件**：有 Windows 环境实跑一次（重点看：`Get-PayloadDiff` 是否正确识别
  「内容不同」与「缺失」、是否只动已安装 scope）。
- **证据在哪**：团队仓库的 `update-plugins.ps1`。
- **2026-09-23 更新**：用户确认该 ps1 **已验证过**；本机仍无 pwsh，无法独立复核，
  采信用户结论。→ 可关闭（留档待确认是否移入「已完成」）。

## 5. 经验侧：会话经验 / 偏好的检测机制

- **现象**：跨项目通用的偏好被**多个项目各沉淀一份**；会话产生的经验不自动沉淀，靠 Claude
  自决会漏（实测：某轮会话的新事实一条没进 memory）。
- **已完成（2026-09-23）**：
  1. **建归宿**——工作约定类进 `conventions` 资产；个人专属进 `~/.claude/CLAUDE.md`（已瘦身）。
  2. **修通路**——原计划「另建个人私有仓库」**已被推翻**：内容作为资产存在 `ai-dev-kit`
     仓库，本机 `~/.claude/rules/conventions.md` 软链过去，`install.sh` 一键装好。详见 #6。
  3. **判据盲测**——两个全新 agent、中性 prompt、无答案泄漏。**判据成立**：recall 命中已知
     纠正（「不是关到私人仓库」），并且**捞出一条真漏**「先查清再做」（已补进 `CONVENTIONS.md`）。
- **剩下：扫描机制**（并入周检）。盲测暴露两个**必带条件**：
  - **查重须覆盖全部载体**——只比对 `CONVENTIONS.md` 几乎不降噪（14 → 10），因为它看不见
    `DESIGN.md` / `README` / `BACKLOG` / 规则里的已有结论。
  - **定义要收紧**——「只收**工作约定**，不收系统设计决策」（后者已有归宿）。
  - 成本实测：每会话 1 次 LLM 调用（~35k tokens / 13–28s）。
- **触发条件**：并入周检即可做；若噪声仍高，先只覆盖**信号最强的两类**（显式指令 / 明确纠正）。
- **证据在哪**：`DESIGN.md` §八。

## 6. conventions 插件的 hook 路径未实机验证

- **现象**：`plugins/conventions` 有两条交付路——用户级规则（本机，**已验证生效**）与插件
  `SessionStart` hook（分发用）。**hook 那条从未在真实环境装过**：`${CLAUDE_PLUGIN_ROOT}`
  能否解析、hook 是否真触发、注入内容是否进上下文，都只是照文档写的，**没跑过一次**。
- **为什么现在不做**：本机走规则路径即可，插件当前无使用者；且本机也不便验证——装插件会
  与规则**重复加载**。
- **触发条件**：**首次要分发给他人**（或新机器想走插件路径）时，先装一次实跑确认：
  ① `/context` 能看到约定内容；② `${CLAUDE_PLUGIN_ROOT}` 解析正确；③ 无报错。
- **证据在哪**：`README.md`「两种交付方式」；`plugins/conventions/hooks/hooks.json`。

## 已完成（留档，勿重复做）

- **设计文档纳入版本控制**（2026-09-23）。原条目：本体系最完整的推理只活在
  一份被 gitignore 的本机文件里，「本仓库只有结论，没有推理」。
  定案：**去语境化**后作为 `DESIGN.md` 进本仓库根目录——标识符（组织名/仓库名/项目名/
  机器路径）换成角色名，方法论、实测数字、失败模式全部保留；逐条调查过程由 git 历史承载。
  **教训**：文档该跟代码走；跨层的系统设计不该躺在某个业务项目的私有目录里。
- **决策日志的落点**（2026-09-22，绕了两圈才落定）。原条目是「决策集中一处会让项目层
  资产的业务语境进公共仓库」。三次尝试：①集中公共仓库 → 泄漏业务语境；②按**资产所属层**
  分文件 → 把用户级工具状态散写进了 4 个业务项目；③**全部本机**（`~/.claude/`）← 最终。
  定案依据四条事实：与工具「输出不过仓库」的既定原则一致、抑制的噪声本身是本机的、
  写进共享仓库会导致 union 合并后"最新"顺序无意义（该 union 配置已随方案一并移除）、变更理由本就该写在那个变更的
  commit 里。**教训**：先问"这东西的作用域是什么"，再问"放哪"——前两次都是没分清
  「本机使用判断」与「对共享能力的立场」。
- **晋升候选落账通道**（2026-09-22 接入）。原条目：候选被检出却无处落裁决——`decision_log`
  的 `--action` 只有 `keep|retire`，承载不了「上移」。触发条件是「落过第一笔真实裁决」，
  该条件成立后即接入：`--action` 扩为 `keep|retire|promote|hold`（放置侧用 promote/hold），
  两个扫描器都改为**先查裁决再入队**（已裁决的退出队列，ttl 到期才重回）。
