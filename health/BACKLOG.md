# health/ 未接入项（Backlog）

> **为什么有这个文件**：缺口如果只活在某个人的记忆里、或一份 gitignore 掉的本机计划文件里，
> 就等于没记——这正是本工具自己在治的病（「证据过期 = 假阴性」「决策不落账 = 没有』低频『只有』无数据『」）。
> 所以未接入项要和代码放在一起、进版本控制、每项带**触发条件**。
>
> **用法**：不要定期通读。当某项的**触发条件**出现时，来做它。
> 触发条件写的是"什么事实出现就该动手"，不是一个日期——日期会过期，事实不会。
>
> 最后更新：2026-09-22

## 1. 设计文档未纳入版本控制

- **现象**：本体系最完整的推理（三层划分、市场对齐、为何这样取舍、全部实测结论）
  写在本机一份被 gitignore 的计划文件里（不在本仓库，且与一个业务项目同目录）。
  **本仓库只有结论，没有推理**；换设备/换人都拿不到。
- **为什么现在不做**：它是个人计划产物，含大量跨项目语境，直接搬进公共层会污染"去语境化"原则。
- **触发条件**：需要**作者以外的人**理解这些取舍时（他人接手 / 团队要评审这套引擎 / 换设备重装）。
  届时抽出去语境化的部分进本仓库（如 `health/DESIGN.md`），保留完整版在计划文件。
- **证据在哪**：本仓库 README 与各脚本注释是它的摘要。

## 2. Windows 无通知、无调度

- **现象**：三个 Python 脚本跨平台，但 `install.sh`（launchd）与 `skill-health-check.sh`（osascript）
  是 macOS 专有。Windows 用户只能手动跑脚本，收不到通知、也没有自动巡检。
- **为什么现在不做**：开发机无 Windows / 无 pwsh，**一行都验证不了**；
  而静默失效的调度注册比没有更糟（让人以为监控开着）。
- **触发条件**：有可实跑的 Windows 环境（或团队确实有 Windows 使用者提出需要）。
  交付物：`skill-health-check.ps1` + 一次性计划任务注册，需在 Windows 上实跑确认。
- **证据在哪**：README「平台边界」表。

## 3. 流水线 B：回归门禁（防退化）

- **现象**：没有任何"谁做得好"的度量。用量侧只能回答"谁没人用"，
  驱动得了**退役**，驱动不了**改进**。
- **为什么现在不做**：原计划的推迟理由是"待数据积累"——但该理由**自我否定**：
  转录 30 天过期、且裁决端从未触发，不主动做就永远不会积累。
  另一条否决：不建通用 eval，应从真实转录里挖**失败证据**（用户纠正/重做、
  以及 gen-commit 提议 vs 实际 `git log` 这类确定性信号）→ 聚类 → 出 SKILL.md diff → 小样本 A/B。
- **触发条件**：需要一个能力**变好**而不只是"没人用就退役"时；
  或某个 skill/agent 出现重复性失败（`scan_skill_usage.py` 的失败列非零且成簇）。
- **证据在哪**：设计文档 §4.2 流水线 B；`scan_skill_usage.py` 的 `failures` 列（现已接通，当前全 0）。

## 4. 流水线 C：漂移检测

- **现象**：官方 marketplace 或依赖（graphify）大版本更新时，没有任何自动检测，
  全靠人"想起来去看"。
- **为什么现在不做**：尚无因上游变更造成实际损害的案例。
- **触发条件**：官方/依赖更新**实际打断过**本套能力（如官方 code-review 改了语义、
  graphify 命令变更导致 `graphify-search` 失效）。
- **证据在哪**：设计文档 §4.3。

## 5. `update-plugins.ps1` 未经验证

- **现象**：团队仓库的 `update-plugins.ps1` 与 `.sh` 逻辑等价（内容指纹判定
  + 只处理已安装 scope），但**从未在 PowerShell 里跑过**。
- **为什么现在不做**：开发机无 pwsh。已写成「指纹计算失败即降级回原有 update 行为」，
  最坏情况是退化成旧行为而非报错中断，风险有界。
- **触发条件**：有 Windows 环境实跑一次（重点看：`Get-PayloadDiff` 是否正确识别
  「内容不同」与「缺失」、是否只动已安装 scope）。
- **证据在哪**：团队仓库的 `update-plugins.ps1`。
